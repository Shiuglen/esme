## 1. El formato de una skill

### 1.1 Hay especificación abierta [H]

- Nombre: **Agent Skills**. Sitio y especificación en https://agentskills.io (`/specification`). Desarrollada por Anthropic, publicada como estándar abierto y adoptada por muchos productos (https://agentskills.io/home). Repo de la especificación: https://github.com/agentskills/agentskills (Apache-2.0 según la API de GitHub, último push 2026-08-09). Validador de referencia: `skills-ref validate ./mi-skill` (en ese repo).
- La lista de clientes de esa página incluye, entre otros: Claude Code, Claude, Codex (ChatGPT), Gemini CLI, OpenCode, Cursor, Goose, GitHub Copilot, VS Code, Roo Code, Kiro, Amp, Factory, OpenHands, Junie.

### 1.2 Estructura [H] (https://agentskills.io/specification)

```
nombre-skill/
├── SKILL.md        # obligatorio: frontmatter YAML + Markdown
├── scripts/        # opcional: código ejecutable
├── references/     # opcional: documentación que se carga bajo demanda
├── assets/         # opcional: plantillas, imágenes, datos
└── ...             # cualquier otra cosa
```

Frontmatter de la especificación abierta:

| Campo | Obligatorio | Restricciones |
|---|---|---|
| `name` | Sí | 1-64 caracteres; minúsculas, números y guiones; sin guion al inicio/fin ni `--`; **debe coincidir con el nombre de la carpeta** |
| `description` | Sí | 1-1024 caracteres; qué hace y cuándo usarla |
| `license` | No | Nombre de licencia o fichero incluido |
| `compatibility` | No | Hasta 500 caracteres; requisitos de entorno |
| `metadata` | No | Mapa de cadenas a cadenas |
| `allowed-tools` | No | Cadena con herramientas preaprobadas separadas por espacios. Marcado **experimental** |

- Carga progresiva en tres niveles: metadatos (~100 tokens por skill, siempre), cuerpo de `SKILL.md` (recomendado < 5000 tokens, < 500 líneas) y recursos (solo si hacen falta). Las referencias a ficheros son relativas a la raíz de la skill y a un solo nivel de profundidad.

### 1.3 Extensiones propias de cada agente (no son portables) [H]

- **Claude Code** (https://code.claude.com/docs/en/skills): todos los campos son opcionales; añade `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `hooks`, `paths`, `shell`. Los campos desconocidos se ignoran en silencio. Fuera de Claude Code (claude.ai, API de Skills) solo se admiten los seis campos del estándar y cualquier otro da error de validación. Admite `` !`comando` `` que se ejecuta antes de que el modelo vea el texto.
- **Qwen Code**: `name` admite letras, dígitos, `_`, `:`, `.`, `-` (más laxo), más `priority`, `paths`, `user-invocable`, `disable-model-invocation`, `hooks` (https://qwenlm.github.io/qwen-code-docs/en/users/features/skills/).
- **OpenCode**: `metadata` con claves `opencode/slash` y `opencode/autoinvoke` (https://opencode.ai/docs/skills/).
- **Codex**: fichero opcional `agents/openai.yaml` dentro de la skill (`policy.allow_implicit_invocation`, `dependencies.tools`) (https://learn.chatgpt.com/docs/build-skills, redirige desde developers.openai.com/codex/skills).
- **Cursor**: `paths` (antes `globs`), `disable-model-invocation`, `icon`, `color` (https://cursor.com/docs/context/skills).
- **[I]** Conclusión: una skill que solo use los seis campos del estándar es portable a todos los agentes. Las skills con campos de Claude funcionan en los demás, pero pierden esas funciones, sin error.

Detalles que importan:

- **Soporte real, no solo documentado**: los ocho lo documentan como función normal. - **Cline** activa las skills descubiertas por defecto y tiene un conmutador por skill en su panel. **Codex** las desactiva con `[[skills.config]] path=... enabled=false` en `~/.codex/config.toml`. **Goose** trae la extensión Skills activada por defecto. **OpenCode** permite `permission.skill` con `allow/deny/ask` en `opencode.json`.
- **Codex no fusiona** skills con el mismo `name`: aparecen ambas. **[I]** Instalar la misma skill en varias rutas que un mismo agente lee provoca duplicados en su lista (OpenCode lee tres rutas de usuario).
- **Claude vía ACP (`claude-agent-acp`)**: el adaptador usa el Claude Agent SDK (https://github.com/agentclientprotocol/claude-agent-acp, Apache-2.0). El SDK descubre skills solo si `settingSources` incluye `user` y/o `project`; con las opciones por defecto de `query()` las carga (https://code.claude.com/docs/en/agent-sdk/skills) [H]. **[?]** No comprobé qué `settingSources` fija el adaptador. Hay que probarlo con una skill de prueba y mirar el mensaje `init` (campo `skills`). En Esme, la decisión vigente es Claude en PTY con el binario sin modificar (docs/investigacion/2026-10-11-app-arquitectura.md), donde `~/.claude/skills` aplica con seguridad.
- **Codex vía `codex-acp`**: **[I]** al envolver el núcleo de Codex debería leer `~/.agents/skills`, pero no lo comprobé; hay que probarlo.

Consecuencias para el diseño:
- Hay que **tolerar enlaces rotos** en las carpetas destino (no seguirlos, no fallar, no borrarlos).

La interfaz debe mostrar el recuento por agente y avisar al pasar de un umbral (propuesto: 30).
- Cuando una carpeta destino no existe (Codex, Gemini...), el agente probablemente no está instalado; la UI debe ofrecer solo los motores detectados por `motores/which.ts`.

## 4. Riesgos de seguridad y mitigaciones

### 4.1 Riesgos documentados [H]

- **Guía oficial de Anthropic** (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview#security-considerations): usar skills solo de fuentes de confianza; una skill maliciosa puede dirigir al agente a invocar herramientas o ejecutar código que no corresponde a su propósito (exfiltración de datos, acceso no autorizado). Las skills que descargan contenido externo son de especial riesgo, incluso si luego cambian sus dependencias. En Claude Code las skills tienen el mismo acceso de red que cualquier programa del usuario.
- **Lista de revisión de Anthropic** (https://platform.claude.com/docs/en/agents-and-tools/agent-skills/enterprise): riesgo alto en scripts (`*.py/*.sh/*.js`), directivas que ordenan ignorar reglas o ocultar acciones, referencias a servidores MCP, patrones de red (`curl`, `fetch`, `requests`), credenciales en el texto; riesgo medio en rutas fuera de la carpeta, globs amplios y `../`. Recomienda revisar **todos** los ficheros, fijar versión, calcular sumas de verificación de lo revisado y usar commits firmados. Los autores no deben revisar su propia skill.
- **`allowed-tools` es una preaprobación, no una restricción**: salta los avisos de permiso durante el turno. Hay que revisarlo antes de ejecutar en un repo ajeno. Existe `disableSkillShellExecution` para desactivar `` !`cmd` `` (https://code.claude.com/docs/en/skills).
- **Estudio ToxicSkills de Snyk (2026-02-05)** (https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub), informe de un proveedor que promociona sus herramientas: 3984 skills de ClawHub y skills.sh; 13,4 % con al menos un problema crítico; 36,8 % con alguno de cualquier gravedad; 76 cargas maliciosas confirmadas por revisión humana. Técnicas: instrucciones ocultas (base64, caracteres Unicode invisibles, «ignora las instrucciones anteriores»), scripts con puertas traseras o robo de credenciales, descargas de binarios (zips con contraseña), exfiltración ofuscada y carga remota de instrucciones en tiempo de ejecución (cambia el comportamiento después de la revisión). Mitigación que propone: `uvx mcp-scan@latest --skills`.
- Los repos grandes de confianza también salen en las auditorías: skills.sh marca como riesgo medio varias de mattpocock y hyperframes, y como alto una de diseño móvil (https://skills.sh/audits). **[I]** Los auditores dan señales, no veredictos; no hay que ocultar una skill por un «medio», sino mostrarlo.

### 4.2 Cómo lo mitigan otros [H salvo lo marcado]

| Mitigación | Quién |
|---|---|
| Aviso de seguridad y consentimiento al instalar (`--consent` para saltarlo); instalación desde git con `--path`; desinstalación con `gemini skills uninstall` | Gemini CLI |
| Auditorías automáticas por terceros mostradas junto a la skill (Gen, Socket, Snyk) | skills.sh |

| Instalación por enlace simbólico con una única copia canónica, o `--copy` | `npx skills` |
| Límites de tamaño y de número de ficheros al extraer | `npx skills` |

## 5. Propuesta de diseño para Esme

Principio: **el catálogo es una lista corta, firmada y revisada por Esme; el contenido viene siempre del repositorio del autor, fijado a un commit; nada se instala sin vista previa y permiso; los scripts van desactivados por defecto.**

### 5.1 De dónde sale el catálogo

1. **Catálogo propio firmado** (`skills-catalogo.json`), con el mismo mecanismo que ya usa la Tienda (`app/src/main/tienda/catalogo.ts`: `firmarCatalogo` / `verificarCatalogo`, clave pública en la app). Hoy `TipoProducto` es `'piel' | 'herramienta' | 'agente' | 'app'`; propongo añadir `'skill'` y un `contenido` con este esquema:

```json
{
  "id": "mattpocock/tdd",
  "tipo": "skill",
  "contenido": {
    "repo": "mattpocock/skills",
    "ruta": "skills/engineering/tdd",
    "commit": "<sha completo revisado>",
    "arbolSha256": "<hash del contenido revisado>",
    "licencia": "MIT",
    "paquete": null,
    "tieneScripts": false,
    "camposNoEstandar": [],
    "revisadoPor": "esme",
    "revisadoEl": "2026-10-19"
  }
}
```
   - Solo entran skills con licencia permisiva comprobada **por carpeta** (sección 3.2). Las propietarias (`docx/pdf/pptx/xlsx` de Anthropic) quedan fuera.
   - Fijar `commit` y `arbolSha256` implementa la «verificación de integridad» y «versión fijada» que recomienda Anthropic: si el autor cambia el repo, Esme sigue instalando lo que se revisó, y un botón «Actualizar» muestra un diff antes de aceptar.
2. **Descarga**: tarball de `codeload.github.com/{repo}/tar.gz/{commit}` (sin autenticación, sin token), extracción solo de la subcarpeta, con los mismos límites que `npx skills` (10 MiB descargado, 25 MiB extraído, 1000 ficheros) y rechazo de enlaces simbólicos y rutas con `..`. **[I]** No uso `npx skills` ni su telemetría; no hace falta Node ni red extra y el comportamiento es el mío.
3. **Exploración opcional** («Buscar fuera del catálogo»): URL de un repo de GitHub pegada por el usuario, marcada «sin revisar», con las mismas comprobaciones y un aviso más fuerte. No usar la API de skills.sh (exige OIDC de Vercel). Las auditorías de skills.sh solo se mostrarían si algún día hay acceso estable **[?]**.
4. **Paquetes**: el catálogo agrupa skills dependientes (por ejemplo, las de Superpowers) en un paquete que se instala entero.

### 5.2 Cómo se instala para cada agente (rutas verificadas)

- **Copia canónica única** en la carpeta de datos de Esme: `<datos de Esme>/skills/<nombre>/` con un fichero `.esme-skill.json` (repo, commit, hash, licencia, fecha, agentes instalados). La propia Esme (chat con Vercel AI SDK) lee de ahí: carga `name`+`description` en el prompt y expone una herramienta `cargar_skill(nombre)` que devuelve el `SKILL.md` y deja leer sus ficheros. **[I]** Es lo que hace cualquier cliente del estándar; Esme debe implementarlo porque no es un agente de terminal.
- **Destinos por agente** (usuario, todos en el directorio personal; el proyecto es opcional y solo a petición):

| Motor del Taller (`acp-motores.ts`) | Carpeta destino de usuario | Comprobada en este equipo |
|---|---|---|
| Claude (PTY y adaptador ACP) | `~/.claude/skills/<n>/` | Existe |
| Codex (`codex-acp`) | `~/.agents/skills/<n>/` | No existe; crearla con permiso. La lectura por `codex-acp` es [?] |
| OpenCode | `~/.config/opencode/skills/<n>/` | Existe |
| Qwen Code | `~/.qwen/skills/<n>/` | Existe, vacía |
| Gemini CLI | `~/.gemini/skills/<n>/` (o `~/.agents/skills/` si ya se usa para Codex) | No existe |
| Cline | `~/.cline/skills/<n>/` | `~/.cline` existe, `skills/` no |
| Cursor / Goose (si se añaden) | `~/.cursor/skills/` / `~/.agents/skills/` | No existen |

- **Evitar duplicados [I]**: OpenCode, Cursor y Goose ya leen también `~/.claude/skills` y/o `~/.agents/skills`. Regla: cada skill se instala en **la carpeta propia de cada agente elegido** y Esme calcula, con una tabla de «quién lee qué» (la 2.1), si un agente verá la misma skill por dos rutas; en ese caso avisa y no crea la segunda copia. Ejemplo: Codex y Gemini comparten `~/.agents/skills/` (una sola entrada); OpenCode ya vería la de Claude en `~/.claude/skills/`, así que, si el usuario marca Claude y OpenCode, solo se instala una vez (Claude) y se anota que OpenCode la lee de ahí.
- **Método**: enlace simbólico a la copia canónica en Linux/macOS (una sola copia, actualizaciones centralizadas); copia real en Windows o si falla el enlace (los permisos de enlaces en Windows requieren privilegios [I]). Es la misma elección que hace `npx skills --copy`. Tolerar enlaces rotos ya presentes en el destino (hay 26 aquí).
- **Prueba de carga tras instalar**: ejecutar `SKILL.md` por el validador (reglas de la 1.2: `name` = nombre de carpeta, longitudes) y, si el agente lo permite, comprobar que aparece (Claude: campo `skills` del mensaje `init`; OpenCode/Gemini: sus comandos de listado). Si el agente estaba en marcha, avisar de que hay que reiniciar la sesión (Codex pide reiniciar tras instalar; Claude recarga en vivo salvo carpetas nuevas) [H].
- **Reglas de nombre**: conflicto de `name` con una skill ajena del usuario ⇒ no sobrescribir; ofrecer instalar con prefijo `esme-<nombre>` (sin tocar el contenido). No usar carpetas reservadas (`synced`, `anthropic-skills`) [H].

### 5.3 Cómo se ve antes de instalar

Ficha con tres zonas, siempre accesible sin instalar nada (la descarga se hace a una carpeta temporal aislada):

1. **Resumen**: nombre, descripción (completa, es lo que el modelo leerá siempre), autor y repo (enlace), licencia, commit, tamaño, coste estimado en tokens (metadatos + cuerpo, **[I]** estimación por caracteres / 4), agentes compatibles y qué ruta se va a escribir en cada uno.
2. **Contenido**: árbol de ficheros y visor de `SKILL.md` con el Markdown renderizado y un conmutador «texto sin procesar» que enseña el fuente tal cual (con caracteres Unicode invisibles y etiquetas HTML ocultas resaltados). Cada fichero es abrible.
3. **Alertas** calculadas localmente (heurísticas de la sección 4, basadas en la lista de Anthropic y en las técnicas de Snyk):
   - Hay `scripts/` o ficheros ejecutables (`.py .sh .js .ts .ps1 .exe`, bit de ejecución): **nivel alto**.
   - Campos que preaprueban o ejecutan: `allowed-tools`, `hooks`, `context: fork`, `` !`cmd` `` en el cuerpo: **alto**.
   - Patrones de red o descarga: `curl`, `wget`, `fetch`, `requests`, URLs en scripts, `npx`/`pip install`/`uvx`: **alto**.
   - Ofuscación: bloques base64 largos, `eval`, `exec`, caracteres de ancho cero o etiquetas Unicode, HTML con `display:none` o comentarios largos: **alto**.
   - Frases de manipulación («ignora las instrucciones anteriores», «no se lo digas al usuario»): **alto**.
   - Referencias a servidores MCP, a rutas fuera de la carpeta, a `~/.ssh`, `.env`, claves: **medio**.
   - Secretos escritos en el texto: **alto**.
   - Tamaño anómalo (> 500 líneas en `SKILL.md`, > 1 MiB en total) y `name` que no coincide con la carpeta: **aviso**.
   Si el hash del árbol no coincide con el del catálogo, bloquear (y mostrarlo como posible manipulación).
4. **Permiso**: botón «Instalar» con selector de agentes (marcados los detectados). Texto exacto de lo que se escribirá y dónde. Sin instalación silenciosa ni por orden de un agente o de un texto web. Si se suma una skill con scripts, un segundo consentimiento explícito.

### 5.4 Scripts: desactivados por defecto

- **Instalación «solo texto»** (por defecto): copia `SKILL.md`, `references/`, `assets/` y ficheros de texto; **omite `scripts/`** y lo anota (`scriptsOmitidos: true`). **[I]** Muchas skills de instrucciones funcionan sin scripts; las que dependen de ellos (ej. `webapp-testing`) se marcan «requiere scripts» en la ficha y no se ofrecen en modo solo texto.
- **Instalación «con scripts»**: requiere abrir el visor de cada script, aceptar una advertencia y, en el Taller, **no aprobar automáticamente** los permisos que esos scripts pidan (se mantiene el sistema de permisos del Taller). Los scripts se copian sin bit de ejecución.
- En los agentes que lo admitan, reforzar con sus propias reglas: `permission.skill: ask` en OpenCode para las skills instaladas por Esme, `[[skills.config]] enabled=false` en Codex si el usuario las desactiva desde Esme, y el conmutador de Cline [H]. **[I]** Esme no debe editar `settings.json` global de Claude ni `opencode.json` del usuario sin un permiso aparte (son cambios de configuración persistente).
- Recomendación de lectura de campos: no modificar el contenido de la skill (rompería el hash); solo advertir. Las skills con `disable-model-invocation: true` se marcan «solo manual».

### 5.5 Cómo se desinstala y se actualiza

- **Manifiesto** `<datos de Esme>/skills/instaladas.json`: por skill, la lista de rutas creadas (enlaces/copias), el commit y el hash.
- **Desinstalar**: elimina **solo** las rutas del manifiesto que sigan teniendo el marcador `.esme-skill.json` con el mismo identificador (o que sean un enlace que apunte a la copia canónica), y después la copia canónica si ya no queda ningún agente. Nunca toca carpetas sin marcador (aunque tengan el mismo nombre), ni enlaces rotos ajenos. Antes de borrar, muestra la lista y pide confirmación; mover a la papelera de Esme en lugar de borrado permanente.
- **Detección de cambios**: si el usuario editó una skill instalada (el hash difiere), «Desinstalar» ofrece guardar una copia y «Actualizar» no la sobrescribe.
- **Actualizar**: el catálogo trae un commit nuevo ⇒ la ficha muestra el diff entre el commit instalado y el nuevo, vuelve a lanzar las alertas y exige permiso otra vez.
- **Reparación**: botón «Comprobar» que detecta enlaces rotos de las skills de Esme, carpetas borradas a mano y skills que el agente no ve.
